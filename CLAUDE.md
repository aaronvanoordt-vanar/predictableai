# predictable.ai — Revenue OS

Spanish-language sales-intelligence SaaS. Static vanilla-JS frontend + Supabase backend (Auth, Postgres with RLS, Realtime, Deno edge functions that call the Anthropic API). No framework, no build step, no bundler.

## ⚠️ main IS production

GitHub Pages serves `main` directly at https://predictableai.vanarsi.com (see `CNAME`). **Merging a PR is a production deploy.** Before opening or updating any PR, run the `/preflight` skill (`.claude/skills/preflight/SKILL.md`). At minimum:

```bash
node scripts/check.mjs   # must print OK
```

## Run locally

```bash
python3 server.py    # or: node server.js — serves the app on :3000 and proxies Apollo API
```

There is no package.json, no npm install, no test suite. Verification = `scripts/check.mjs` + driving the app in a browser (Playwright works in web sessions).

## Architecture

- **Page flow:** `landing.html` → `auth.html` → `auth-callback.html` → `onboarding.html` → `index.html` (the app).
- **`index.html` is a ~5,000-line monolith**: all views, all CSS, and large inline `<script>` blocks (nav/theme, coach/reports, settings/auth UI). Two production outages came from edits here: orphan leftover code causing a `SyntaxError` that killed every inline function (PR #18), and unbalanced `<div>`s causing a black screen on navigation (commit 0a151b4). After ANY edit to it, `node scripts/check.mjs` runs automatically via hook — if it fails, fix before continuing. Prefer adding new features as `js/` modules over growing the inline scripts.
- **Prospección = `js/prospecting.js` (tres vistas: Buscar / Listas / Campañas) + `js/prospecting-data.js` (data layer) + `js/campaigns.js` (vista Campañas)**, mounted into `#prospecting-shell` in page `pro-main`. Lists live in Supabase (`prospect_lists` / `prospect_list_members`), NOT localStorage. **El journey es lineal: Buscar → Listas (contactos, enriquecimiento y estados en la misma pantalla; "Todos los contactos" es una pseudo-lista) → Campañas.** Las pestañas Resumen, Contactos, Secuencias (secuencias de Apollo), Bandeja y Generador de mensajes IA se eliminaron el 2026-09-03 a petición del usuario: los mensajes IA se generan por paso dentro de la campaña y se previsualizan por lead ahí mismo; las respuestas de todos los canales viven en la Bandeja (ítem propio del sidebar). No las resucites como pestañas aparte. The old inline "Apollo Prospecting Engine" and `js/apollo-sequences.js` were removed (PR #31) — do not resurrect them. **«Importar desde Apollo» (Listas) también se eliminó el 2026-09-23**: con la key compartida de la plataforma mostraba las listas de Apollo de todos los clientes a todos; las búsquedas y listas se guardan solo en Predictable, por usuario. `apollo-proxy` ya no permite `/labels` ni `/contacts/search` — no lo resucites. **Con la key compartida tampoco se escribe ni se lee lo guardado en esa cuenta** (`_shared/apollo-platform.ts`, `deno test`): `POST /contacts` responde `{ contact: null }` sin llegar a Apollo y `/mixed_people/api_search` entrega los `contacts` como personas sin email, teléfono ni etiquetas — antes cada «Agregar a lista» dejaba el lead en la cuenta común y la búsqueda de otro cliente lo mostraba como «Guardado» con el email revelado.
- **Campañas omnicanal = `js/campaigns.js` (canales, lista, detalle, enrolar, bandeja de respuestas y de revisión) + `js/campaign-builder.js` (asistente de 4 pasos con la línea de tiempo gráfica de la cadencia; no toca la base, devuelve el borrador por `onSave`) + edge functions `campaign-run` (motor, pg_cron cada minuto, con JWT: lo llama la service role), `generate-campaign` (cadencia recomendada por IA, 6 créditos), `channel-connect` (conectar Email/WhatsApp/LinkedIn), `inbox-send` (responder desde la bandeja) y `wati-webhook` (público, `--no-verify-jwt`).** **Los canales viven DENTRO de Campañas** (barra de canales arriba: son el gate para lanzar campañas; con cero canales conectados la vista es el asistente de conexión). **En la UI los canales se llaman Email, WhatsApp y LinkedIn; los proveedores (Apollo, WATI, Dripify) solo aparecen dentro del asistente de conexión**, porque WATI y Dripify no tienen OAuth ni API de partner: el usuario sigue pegando un token, guiado paso a paso, con un camino "Todavía no tengo cuenta → Crear mi cuenta". **Email/Apollo = OAuth por usuario (opción B, 2026-09-03)**: `channel-connect` `apollo_auth_url`/`apollo_connect` + `apollo-callback.html`; `_shared/apollo-auth.ts` resuelve el token del usuario y cae a la key de la plataforma (`APOLLO_API_KEY`, beta) si no conectó su Apollo. **Ese fallback es SOLO para buscar y enriquecer: el canal de Email exige cuenta propia, igual que WhatsApp y LinkedIn** (2026-09-13). Con la key compartida, `apollo-proxy` rechaza `/email_accounts` y `/emailer_*` con 403 `apollo_account_required`, y `campaign-run`/`inbox-send` no envían — mostrarla como conectada le enseñaba a cada cliente nuevo el buzón del dueño de la plataforma como si fuera suyo. En modo OAuth los reveals no cobran créditos de la plataforma (los paga el Apollo del cliente). **LinkedIn no tiene tope diario en la UI ni en el motor**: el ritmo lo decide Dripify (Activity Control). Diseño, decisiones y hallazgos de las APIs en `docs/OMNICANAL.md`. **Bandeja omnicanal (2026-09-14) = la vista `inbox` de `js/campaigns.js` (entrada "Bandeja" en la barra lateral, `window.campaigns.setView('inbox')`)**. **Esa entrada del sidebar es la ÚNICA**: la pestaña "Bandeja" que vivía dentro de Campañas se borró el 2026-09-15 (era el mismo panel por dos caminos) — no la resucites; el contador de mensajes sin leer vive ahora en `#nav-bandeja-badge` del sidebar (`updateBadge()`). Muestra TODO `inbox_messages` (enviado y recibido por los tres canales, también contactos sin lista, que se pueden guardar en una lista) y responde por WhatsApp (WATI: texto o plantilla de saludo si la ventana de 24 h se cerró) y email (Apollo). **LinkedIn no se puede enviar por API** (Dripify es de solo lectura: la respuesta se copia y se pega en el chat). **El botón "Redactar con IA" de la bandeja (2026-09-15) es la ÚNICA generación de mensajes fuera de una campaña**: `generate-outreach` en modo `reply` escribe un borrador con el hilo real (3 créditos) y lo deja en el cuadro de texto para editarlo; nunca se envía solo. **Campañas de LinkedIn diseñadas en Predictable = `js/linkedin-campaigns.js` + tabla `linkedin_campaigns`**: Dripify tampoco permite crear campañas por API, así que se diseñan aquí y se vinculan por nombre a la que el usuario crea en Dripify (el motor las vincula solo cuando existen); los nodos de LinkedIn aceptan `settings.linkedin_campaign_id` o `settings.dripify_campaign_id`. **Una campaña de Dripify = UN solo envío (2026-09-15)**: `linkedin_connect` apunta a una de `purpose = 'connect'` (solo la solicitud) y `linkedin_message` a una de `purpose = 'message'` (solo un mensaje, y solo si el lead ya aceptó la conexión). Una campaña de Dripify con su propia secuencia la ejecuta Dripify sola y sigue escribiendo aunque el lead ya haya respondido por otro canal — la regla de parada no alcanza allá. Un lead pasa por varias campañas de Dripify: `provider_refs.dripify_uploads` (dedupe por campaña) y `dripify_last_action_by` (cursor por campaña). **Un lead sin teléfono / email / URL no detiene la cadencia**: el paso se omite (`skipped`) y sigue con el siguiente; un rechazo del proveedor en un envío es `failed` y también sigue. **Tampoco la detiene una plantilla de WhatsApp muerta** (DELETED, PENDING_DELETION, REJECTED, PAUSED, DISABLED, ARCHIVED): esos estados son terminales, el paso se omite y el lead sigue con el canal siguiente — nunca un `hold` que se reintente cada 6 h para siempre (el 2026-09-14 eso dejó 100 leads clavados en el "Saludo 1" de una plantilla borrada, sin llegar al email que venía después). La clasificación vive en `supabase/functions/_shared/wati.ts` (`isTemplateDead`, cubierto por `deno test`) y se espeja en `js/campaigns.js` + `js/campaign-builder.js`. `sync_templates` de `channel-connect` es lo que repara el canal: una ranura muerta se recrea con el nombre de la revisión siguiente (`px_hola_1_v3_<hash>_r2`), porque Meta no revive una plantilla borrada ni deja reusar su nombre en 30 días — antes reconectar el canal no la recreaba (el nombre es determinista y la fila muerta se daba por buena). En Campañas, el botón "Reintentar N retenidos" adelanta a ahora los enrolamientos activos con `error_detail`. **Las plantillas se sincronizan en los dos sentidos** (2026-09-14): `sync_templates` guarda además el catálogo COMPLETO del tenant en `channel_accounts.config.templates.all` con el estado que puso Meta, y desde la pestaña de WhatsApp se crean (`create_template`) y se borran (`delete_template`, que necesita el `waba_id` de `config.phone_numbers`) plantillas propias; la bandeja puede reabrir la ventana de 24 h con cualquiera aprobada, no solo con las de saludo. **La API de WATI solo permite CREAR webhooks** — listarlos, editarlos o borrarlos responde 405, y el tenant tiene un tope, así que con el cupo lleno el registro automático falla aunque la URL correcta ya esté puesta a mano; la única prueba de que funciona es que WATI nos llame, y por eso `wati-webhook` sella `config.webhook.last_received_at`. No vuelvas a poner el aviso rojo a depender de `webhook.registered` a secas ni a reintentar el POST sobre un registro que ya funcionaba. **La cadencia que ejecuta el motor es el grafo `campaigns.flow`** (acciones + condiciones con ramas Sí/No, espera relativa al paso anterior): esquema, validación y recorrido en `supabase/functions/_shared/campaign-flow.ts` ↔ `js/campaign-flow.js`, **espejos exactos que se cambian juntos en el mismo PR** (`deno test` cubre el TS). Regla de parada fija: una respuesta por cualquier canal, la baja o la detención manual. **Por eso NO existe una condición "¿respondió?"** (su rama Sí nunca se recorrería) ni "¿hizo clic?" (Apollo no reporta clics de un `emailer_message` individual): las condiciones son `linkedin_connection_sent`, `linkedin_connected`, `whatsapp_delivered`, `whatsapp_read`, `email_delivered`, `email_opened`, `email_bounced`, `engaged_any`, `has_phone`, `has_email`, `has_linkedin`. No inventes señales que ningún proveedor reporta. El mensaje IA de cada paso vive en `campaign_messages` (solo el motor inserta; el cliente edita texto y aprueba) y lo genera `generate-outreach` en modo `step` 24 h antes de cada envío, con el ángulo y las instrucciones de ESE paso. **Los mensajes IA son de la campaña, no de la lista (2026-09-15)**: enrolar ya no genera nada, el motor ya no reutiliza `prospect_list_members.outreach` como apertura y la generación desde Listas se eliminó de `js/prospecting.js` (un único texto por lead servía de apertura a toda campaña, ignorando su cadencia). No la resucites ahí. La personalización de 5 capas del lead (`prospect_list_members.outreach`, que alimenta el brief del coach) sigue existiendo, pero su única entrada es el botón **"Preparar con IA" del Meeting Coach** (`js/coach-lead-picker.js`, 3 créditos). ## Motores de IA (Claude / OpenAI / Perplexity)

Cada función con IA puede correr sobre cualquiera de los tres motores. La preferencia vive en `profiles.ai_engines` (JSONB, una clave por función) y se resuelve en dos lugares que **deben mantenerse en sync**:

- `supabase/functions/_shared/llm.ts` — `RECOMMENDED_ENGINE` + `callLLM()`, el único sitio que sabe hablar con cada proveedor (web search, JSON schema, PDFs, reintentos). Toda edge function con IA pasa por aquí; ninguna vuelve a llamar a `api.anthropic.com` directamente.
- `js/ai-engine.js` — `FEATURES` + el selector (`AIEngine.mount(...)` o `<div data-ai-engine="coda">`).

Recomendados: `intel_hub`, `coda` (Contexto estratégico IA), `onboarding` (research inicial/Intelligence Hub) y `radar` (detección de señales) → **Perplexity**; `outreach` y `client_review` (la narrativa de la revisión del portal) → **Claude**; `coach` → **OpenAI**.

Reglas:
- El motor del body de la request es solo un atajo: la edge function **siempre** revalida contra su allowlist y cae al recomendado si no reconoce el valor.
- Si falta la API key del motor elegido (o el motor no puede con esa llamada, p. ej. Perplexity + PDF), `callLLM` cae a Claude y lo loguea — nunca rompe la función.
- Secrets: `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `PERPLEXITY_API_KEY`. Modelos overridables con `OPENAI_MODEL` (default `gpt-5`) y `PERPLEXITY_MODEL` (default `sonar-pro`).
- Excepción conocida: el coach en vivo del navegador (`js/realtime-coach.js`) usa el worker `/openai` cuando el motor es OpenAI; con Claude/Perplexity resuelve el turno en la acción `coachTurn` de `sales-coach`.

## Supabase

- Project config in `js/config.js` (URL + anon key — the anon key is public by design; RLS enforces access).
- `supabase/migrations/` — applied to production. **Never modify an existing migration; always add a new file.** Note in the PR body that a migration must be applied.
- `supabase/functions/` — las edge functions de Deno (`learning-loop`, `enrich-company`, `generate-intel-hub`, `schedule-intel-hub`, `generate-radar`, `radar-plan`, `radar-monitor`, `apollo-proxy`, `apollo-webhook`, `generate-outreach`, `generate-client-brief`, `client-portal`, `sheet-sync`, `channel-connect`, `campaign-run`, `inbox-send`, `wati-webhook`, `dripify-webhook`, …). **`wati-webhook` y `dripify-webhook` se despliegan con `--no-verify-jwt`** (los proveedores las llaman sin JWT; se autentican con `?key=<webhook_secret>` por cuenta). **`sheet-sync` también se despliega con `--no-verify-jwt`** (el portal la llama sin sesión; se autentica sola con el `share_token`, con el JWT del equipo vía RLS, o con `SHEET_SYNC_SECRET` para el cron). They do **not** auto-deploy; say "requires `supabase functions deploy <name>`" in the PR body when you change one. Para desplegarlas sin repo local está el workflow manual **Actions → Deploy Edge Functions** (`.github/workflows/deploy-functions.yml`): corre sobre la rama que elijas, aplica solo `--no-verify-jwt` a las funciones que lo necesitan, y usa el secret `SUPABASE_ACCESS_TOKEN`. **`apollo-webhook` must be deployed with `--no-verify-jwt`** (Apollo calls it; it self-authenticates via `?token=` against `APOLLO_WEBHOOK_SECRET`) — redeploying it with JWT verification silently breaks async phone reveals. **`enrich-company` también corre hoy en producción con `verify_jwt=false`** (se autentica sola: valida el Bearer con `auth.getUser` y devuelve 401 sin usuario), así que redesplegarla sin `--no-verify-jwt` le cambia la configuración — usa la bandera para dejarla como está.
- **All Apollo API calls go through the `apollo-proxy` edge function** (secret `APOLLO_API_KEY`, JWT required). Never call Apollo directly from the client or put its key in any file.
- Key tables: `profiles` (incl. `role`), `sales_reports`, `intelligence_hub_reports`, `client_icp`, `client_brief`, `prospect_lists`/`prospect_list_members` (client-writable, owner-scoped RLS), `campaigns`/`campaign_enrollments` (client-writable) + `campaign_events`/`inbox_messages`/`channel_accounts` (solo service role escribe; el secreto de `channel_accounts` está oculto por grants de columna) + `campaign_messages` (el motor inserta; el cliente solo actualiza `subject`/`body`/`status`), `client_sheet_state`/`client_crm_rows`/`client_metric_snapshots`/`client_reviews` (solo la service role escribe; `authenticated` solo lee vía `can_view_client`), credits. ## Security invariants (violations have shipped before — see docs/SESSION_AUDIT_2026-07-02.md)

1. **Users must never be able to change their own `profiles.role`.** An anti-escalation trigger exists (security-hardening migration). Do not add UI, RLS, or RPC that writes `profiles.role` from the client.
2. **Never insert API/LLM/user data into the DOM via raw `innerHTML`.** Escape it (see `js/ui-helpers.js`) — XSS via Apollo/Supabase/LLM render paths was found and fixed in PR #25.
3. **Never hardcode API keys or secrets** in any file — this repo is publicly served. Secrets belong in Supabase edge-function env vars. (`scripts/check.mjs` scans for this.)
4. New RPC/functions: default-deny — revoke from `anon`/`PUBLIC` unless intentionally public (a credit-draining hole via `decrement_credits` shipped once).
